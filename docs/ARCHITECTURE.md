# Architecture

## Current foundation

- `app/core`: shared runtime configuration and logging.
- `app/book`: book domain boundary, currently empty.
- `app/narrator`: narrator domain boundary, currently empty.
- `app/tts`: text-to-speech boundary, currently empty.
- `app/pipeline`: orchestration boundary, currently empty.
- `app/audio`: audio processing boundary, currently empty.
- `app/ui`: user interface boundary, currently empty.
- `data/`: source and working data.
- `narrators/`: narrator assets and profiles.
- `output/`: generated audiobook output.

## Boundaries not implemented yet

The foundation does not include TTS, LLM, UI, database, or E2A behavior. Future work should keep those integrations behind the package boundaries above and use `app.core.config.load_settings()` for runtime paths and logging settings.

## E2A Integration Decision (Sprint 1 Task 2)

### Chosen integration method

Use E2A as a pinned, isolated subprocess through its headless CLI. Do not import E2A's Python modules: its internal `lib` API is large, stateful, tightly coupled to model and system dependencies, and not a stable application contract. Pin an E2A release (the inspected latest release is `v26.8.20`) and invoke the matching launcher or container image. On Windows, the documented launcher is `ebook2audiobook.cmd`; inside the installation or container the direct entry point is `app.py`.

The future adapter should own argument construction, process lifetime, stdout/stderr capture, output discovery, and translation of process results into application-level progress and errors.

### E2A entry point

```text
ebook2audiobook.cmd --headless ...
python app.py --headless ...
```

The Windows command file provisions/selects E2A's environment and then runs `python -u app.py`. A container entry point is also viable when reproducibility and dependency isolation matter more than native installation; the same `--headless` arguments are passed to the image.

### Configurable E2A Discovery (Sprint 3 Task 8)

The adapter dynamically discovers the E2A entrypoint executable using a strict 4-tier resolution priority:

1. **`E2A_ENTRYPOINT` environment variable:** Explicit file path to the executable launcher (e.g. `C:\E2A\ebook2audiobook.cmd`).
2. **`E2A_ROOT` environment variable:** Directory path to the E2A root directory, combined with `ebook2audiobook.cmd` (or standard launcher scripts).
3. **Existing configured adapter path:** Explicit `entrypoint` argument passed to `E2AAdapter(entrypoint=...)`.
4. **PATH lookup:** Fallback system `PATH` lookup for `ebook2audiobook.cmd` (or `ebook2audiobook`).

#### Diagnostics Protocol
`discover_e2a()` and `E2AAdapter.discovery_info` yield structured diagnostics reporting:
- `resolved_path`: Full path to resolved E2A executable.
- `exists`: Boolean indicating whether the path exists on disk.
- `is_executable`: Boolean indicating executability on the host system.
- `e2a_root`: Detected root directory of the E2A installation.
- `source`: Discovery tier that resolved the path (`E2A_ENTRYPOINT`, `E2A_ROOT`, `configured`, or `PATH`).


### Required arguments and mapping

For one input book, the minimum deterministic invocation is:

```text
app.py --headless --ebook <absolute-input-path> --language <iso-639-code> --output_dir <existing-output-directory> --output_format <format>
```

| Concern | E2A interface | Finding |
| --- | --- | --- |
| Headless mode | `--headless` | Required for a non-GUI invocation. `--ebook`, `--ebooks_dir`, and `--text` are mutually exclusive. |
| Input PDF/EPUB | `--ebook <path>` | Accepts `.pdf` and `.epub`. EPUB generally gives better chapter detection. PDFs are flattened to XHTML; image-only PDF pages trigger OCR and therefore add external dependency/runtime risk. |
| Language | `--language <code>` | Accepts ISO-639-1 or ISO-639-3 according to the CLI. The adapter should pass it explicitly even though E2A has a default. |
| Voice/narrator | `--voice <audio-path>` | Selects a voice-cloning reference audio file; when omitted E2A uses its default voice. This is a file path, not a stable named-narrator ID. For batch mode only, `--voice_map <json-path>` maps ebook paths/basenames to voice paths. |
| Output directory | `--output_dir <path>` | Must already exist according to E2A validation. E2A creates a CLI session subdirectory when this is omitted, so the adapter should provide an explicit directory. |
| Output format | `--output_format <format>` | Supported values include `m4b`, `m4a`, `mp3`, `flac`, `wav`, `ogg`, `aac`, `mp4`, `mov`, and `webm`; default is `m4b`. The final filename is generated by E2A from the input name/metadata, so the adapter must discover and validate the resulting file. |
| Progress | stdout/stderr | E2A emits phase/status messages and `tqdm` progress, including sentence and chapter work. FFmpeg subprocess progress is also consumed internally. There is no documented stable JSON progress protocol; the adapter should treat parsed text as best-effort telemetry and use process completion plus output validation as authoritative. |
| Errors | process result and output | Invalid arguments, missing files/directories, unsupported formats, missing dependencies, conversion failures, and missing/corrupt output are reported as text and result in a failed conversion. The adapter must capture both streams, retain diagnostics, enforce a timeout/cancellation policy, and reject success without a non-empty expected output. |
| Resume | `--session <stable-id>` | Reuses E2A's session state and intermediate sentence/chapter files under its `tmp` directory. E2A stores resume pointers in a per-session SQLite database and JSON state, and can resume at block/sentence granularity. The same session ID, source content, E2A version, model/voice settings, and writable temporary tree must be retained. |

### Integration risks

- **Dependency and environment coupling:** E2A expects its own supported Python environment and external tools such as Calibre, FFmpeg/FFprobe, and often OCR/model runtimes. Native Windows setup can provision Conda/Scoop; a pinned container is more reproducible but requires Docker/WSL and path/volume mapping.
- **CLI output is not an API:** progress is terminal-oriented and may change between releases. Do not make completion depend on a particular progress line; parse defensively and report an indeterminate phase when parsing fails.
- **Voice semantics:** `--voice` is a reference-audio path and E2A may normalize/copy it into session storage. Named narrator catalogs must be resolved by our app before invoking E2A. Changing the global voice on a resumed session can cause affected blocks to be reconverted.
- **Resume is filesystem/state dependent:** E2A's `--session` resume is invalid if its session directory is deleted, the source checksum changes, intermediate files are missing, or the session expires. A changed source can trigger block realignment or a full reconversion.
- **Possible interactive resume prompt:** when prior audio exists, E2A's headless flow can ask whether to skip, resume, or delete and reconvert. The future adapter must either guarantee a fresh/controlled session state or explicitly handle this prompt; otherwise a subprocess can hang waiting for stdin.
- **Input quality:** EPUB has no universal chapter structure, while scanned/image PDFs invoke OCR. Both can produce surprising chapter boundaries or long-running preprocessing.
- **Output naming and partial artifacts:** E2A chooses the final filename and may leave intermediate files after failure. The adapter must use a per-job output directory, validate format and size, and avoid treating stale output as the current run's result.
- **Version drift:** E2A's launcher, flags, defaults, and internal checkpoint layout can change. Pin the release/image and verify the exact `--help` output during adapter startup or installation checks.
